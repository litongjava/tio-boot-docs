# api 管理

[[toc]]

本章完成应用的 API 访问凭证管理：为应用创建 API 密钥，第三方拿着密钥就能直接调用应用的问答接口，不再依赖登录态。除应用密钥外，也提供账号级密钥的接口。前端沿用官方界面，后端接口、密钥认证与数据表在本项目中一并补齐。

## 一、功能范围

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 应用密钥列表 | 已完成 | 按应用归属过滤，密钥原文直接展示，可一键复制 |
| 创建应用密钥 | 已完成 | 服务端生成 `application-` 前缀加 32 位随机串，默认启用 |
| 启用 / 停用密钥 | 已完成 | 停用后带该密钥的请求立即返回 401，无需等待缓存过期 |
| 删除密钥 | 已完成 | 逻辑删除，同时把 `is_active` 置为 `false` |
| 跨域来源配置 | 已完成 | 默认禁止跨域；开启后按来源列表放行，列表为空表示不限制 |
| 账号密钥 | 已完成 | `system-` 前缀，代表密钥所属账号本身，接口与列表结构同构 |
| 密钥调用应用问答 | 已完成 | 密钥可当 Bearer 令牌用，能开会话并流式问答 |
| 密钥访问范围 | 已完成 | 应用密钥只能访问所属应用：带应用 ID 的跨应用请求返回 403，不带应用 ID 的会话路径由会话归属校验兜底 |
| 归属隔离 | 已完成 | 普通账号看不到、也改不了别人的应用密钥 |

密钥的两级设计各管一件事：**应用密钥**给第三方集成用，权限只覆盖它所属的那个应用；**账号密钥**代表账号本身，供账号自己的开放调用使用。两级密钥都只在库里保存密钥本身，不额外保存调用方资料，也不与登录令牌互相转换。

## 二、后端接口

应用密钥挂在应用路径下，账号密钥挂在 `/api/system/api_key` 下。控制器只做参数绑定，归属校验、字段合并等业务规则放在服务层：

```java

    return StrUtil.isBlank(bodyString) ? new JSONObject() : FastJson2Utils.parseObject(bodyString);
  }
```

| 接口 | 行为 |
| --- | --- |
| `GET /api/application/{applicationId}/api_key` | 应用密钥列表，按创建时间倒序，最多 100 条 |
| `POST /api/application/{applicationId}/api_key` | 创建应用密钥，返回新密钥完整记录 |
| `PUT /api/application/{applicationId}/api_key/{apiKeyId}` | 修改启用状态与跨域设置，未提交的字段保持原值 |
| `DELETE /api/application/{applicationId}/api_key/{apiKeyId}` | 逻辑删除应用密钥 |
| `GET /api/system/api_key`、`GET /api/system/api_key/` | 当前账号的密钥列表 |
| `POST /api/system/api_key`、`POST /api/system/api_key/` | 创建账号密钥，返回新密钥完整记录 |
| `PUT /api/system/api_key/{apiKeyId}` | 修改账号密钥的启用状态与跨域设置 |
| `DELETE /api/system/api_key/{apiKeyId}` | 逻辑删除账号密钥 |

路径匹配按段解析，同一个地址带结尾斜杠与不带结尾斜杠等价，因此官方前端对账号密钥的 `PUT`、`DELETE` 使用 `/api/system/api_key/{apiKeyId}/` 也能直接命中；只有纯字面量的列表与新增路径需要成对注册，两种写法都能直接调用。

### 路由优先级

应用密钥接口与应用分页接口共用 `/api/application` 前缀，路由按「固定段更多的模板优先」裁决：`/api/application/{applicationId}/api_key` 的固定段是 `api`、`application`、`api_key` 三段，比 `/api/application/{pageNo}/{pageSize}` 的两段更具体，带 `api_key` 的请求稳定命中密钥接口。这一点在接口层面做过验证：`GET /api/application/{applicationId}/api_key` 返回的是密钥数组，而不是应用分页结果。

### 职责分工

路径模板、路径变量注入、JSON 返回体与统一响应结构都由框架处理，控制器只需要声明路径、参数与返回值，方法里没有一行解析路径的代码；归属校验写在服务层，认证集中在拦截器。这样做的直接好处是：登录令牌与 API 密钥共用同一套鉴权入口，密钥不需要单独开一条业务通道，后续新增接口也不会漏掉鉴权。SQL 用文本块书写，多行语句在源码里保持数据库里能直接执行的排版，排查问题时可以把整段语句原样贴进客户端。

## 三、服务层实现

服务层把每条 SQL 都写成 Java 21 的文本块常量（`"""`），参数全部走占位符，不做字符串拼接。应用密钥的每次读写都带 `application_id` 条件，账号密钥的每次读写都带 `user_id` 条件，越权请求在数据库层就查不到记录：

```java
package nexus.io.maxkb.service.kb;

import java.util.ArrayList;
import java.util.List;
import java.util.UUID;

import com.alibaba.fastjson2.JSONArray;
import com.alibaba.fastjson2.JSONObject;
import com.jfinal.kit.Kv;

import nexus.io.db.activerecord.Db;
import nexus.io.db.activerecord.Row;
import nexus.io.maxkb.constant.MaxKbTableNames;
import nexus.io.maxkb.service.ApiKeyAuth;
import nexus.io.model.result.ResultVo;
import nexus.io.tio.utils.hutool.StrUtil;
import nexus.io.tio.utils.snowflake.SnowflakeIdUtils;

public class MaxKbApiKeyService {

  /** 密钥列表最多返回的条数，避免密钥过多时把界面拖慢。 */
  private static final int KEY_LIMIT = 100;

  /** 单个密钥允许配置的来源数量上限。 */
  private static final int ORIGIN_LIMIT = 32;

  private static final String LIST_APPLICATION_KEYS = """
      select id, secret_key, application_id, user_id, is_active, allow_cross_domain, cross_domain_list, create_time
      from max_kb_application_api_key
      where application_id = ?
        and deleted = 0
      order by create_time desc
      limit %d
      """.formatted(KEY_LIMIT);

  private static final String FIND_APPLICATION_KEY = """
      select id, secret_key, application_id, user_id, is_active, allow_cross_domain, cross_domain_list, create_time
      from max_kb_application_api_key
      where id = ?
        and application_id = ?
        and deleted = 0
      """;

  private static final String UPDATE_APPLICATION_KEY = """
      update max_kb_application_api_key
      set is_active = ?,
          allow_cross_domain = ?,
          cross_domain_list = ?,
          update_time = now()
      where id = ?
        and application_id = ?
        and deleted = 0
      """;

  private static final String DELETE_APPLICATION_KEY = """
      update max_kb_application_api_key
      set deleted = 1,
          is_active = false,
          update_time = now()
      where id = ?
        and application_id = ?
        and deleted = 0
      """;
}
```

列表、创建、修改、删除四个动作都先做一次应用归属校验，再用「主键 + 应用 ID」作为更新条件。修改用「先读后并」的方式处理部分字段：请求里出现的字段覆盖原值，没出现的字段保留原值，因此前端只提交 `is_active` 时不会顺带清掉跨域配置：

```java
  public ResultVo updateApplicationKey(Long userId, Long applicationId, Long apiKeyId, JSONObject input) {
    if (!ApplicationAccess.owns(userId, applicationId)) {
      return ResultVo.fail("应用不存在或无权访问");
    }
    Row existing = Db.findFirst(FIND_APPLICATION_KEY, apiKeyId, applicationId);
    if (existing == null) {
      return ResultVo.fail("密钥不存在");
    }
    int updated = Db.update(UPDATE_APPLICATION_KEY, enabled(input, existing), crossDomain(input, existing),
        (Object) crossDomainList(input, existing), apiKeyId, applicationId);
    return updated == 1 ? ResultVo.ok() : ResultVo.fail("密钥不存在");
  }

  public ResultVo deleteApplicationKey(Long userId, Long applicationId, Long apiKeyId) {
    if (!ApplicationAccess.owns(userId, applicationId)) {
      return ResultVo.fail("应用不存在或无权访问");
    }
    int updated = Db.update(DELETE_APPLICATION_KEY, apiKeyId, applicationId);
    return updated == 1 ? ResultVo.ok() : ResultVo.fail("密钥不存在");
  }
```

账号密钥的服务方法同名同理，只是把条件换成 `user_id`；管理员也不例外，账号密钥始终只属于创建它的账号：

```java
  public ResultVo listUserKeys(Long userId) {
    return ResultVo.ok(toKv(Db.find(LIST_USER_KEYS, userId)));
  }

  public ResultVo updateUserKey(Long userId, Long apiKeyId, JSONObject input) {
    Row existing = Db.findFirst(FIND_USER_KEY, apiKeyId, userId);
    if (existing == null) {
      return ResultVo.fail("密钥不存在");
    }
    int updated = Db.update(UPDATE_USER_KEY, enabled(input, existing), crossDomain(input, existing),
        (Object) crossDomainList(input, existing), apiKeyId, userId);
    return updated == 1 ? ResultVo.ok() : ResultVo.fail("密钥不存在");

```

新建密钥时写入主键、前缀加 32 位随机串、归属与默认值，然后回查一次返回，保证新增与列表返回同一份结构（含 `create_time`）：

```java
  /**
   * 新密钥默认启用、默认不允许跨域，来源列表为空；返回主键供调用方回查，保证新增与列表返回同一份结构。
   */
  private Long insert(String tableName, String prefix, Long userId, Long applicationId) {
    Long apiKeyId = SnowflakeIdUtils.id();
    Row record = Row.by("id", apiKeyId).set("secret_key", prefix + UUID.randomUUID().toString().replace("-", ""))
        .set("user_id", userId).set("is_active", true).set("allow_cross_domain", false)
        .set("cross_domain_list", new String[] {});
    if (applicationId != null) {
      record.set("application_id", applicationId);
    }
    Db.save(tableName, record);
    return apiKeyId;
  }

  public ResultVo createApplicationKey(Long userId, Long applicationId) {
    if (!ApplicationAccess.owns(userId, applicationId)) {
      return ResultVo.fail("应用不存在或无权访问");
    }
    Long apiKeyId = insert(MaxKbTableNames.max_kb_application_api_key, ApiKeyAuth.APPLICATION_PREFIX, userId,
        applicationId);
    return ResultVo.ok(Db.findFirst(FIND_APPLICATION_KEY, apiKeyId, applicationId).toKv());
  }
```

跨域来源列表做去空、去首尾空白和长度限制，最多 32 条、单条不超过 128 字符，避免把任意文本写进数据库：

```java
  private String[] crossDomainList(JSONObject input, Row existing) {
    if (input.containsKey("cross_domain_list")) {
      return origins(input.getJSONArray("cross_domain_list"));
    }
    String[] current = existing.get("cross_domain_list");
    return current == null ? new String[] {} : current;
  }

  /** 来源列表做去空、去空白和长度限制，避免把任意文本写进数据库。 */
  private String[] origins(JSONArray array) {
    List<String> origins = new ArrayList<>();
    if (array != null) {
      for (int i = 0; i < array.size() && origins.size() < ORIGIN_LIMIT; i++) {
        String origin = array.getString(i);
        if (StrUtil.isNotBlank(origin) && origin.trim().length() <= 128) {
          origins.add(origin.trim());
        }
      }
    }
    return origins.toArray(new String[0]);
  }
```

## 四、密钥认证

密钥是不透明字符串而不是 JWT，所以不能走令牌解析。认证器按前缀区分两把钥匙，先在密钥表里查主体，再交给拦截器裁决访问范围：

```java
package nexus.io.maxkb.service;

import nexus.io.db.activerecord.Db;
import nexus.io.db.activerecord.Row;

/**
 * API 密钥解析。密钥是不透明字符串而不是 JWT，因此不能走令牌校验，需要直接在密钥表里查找。
 */
public final class ApiKeyAuth {

  /** 应用密钥前缀。 */
  public static final String APPLICATION_PREFIX = "application-";

  /** 账号密钥前缀。 */
  public static final String USER_PREFIX = "system-";

  private static final String FIND_APPLICATION_KEY = """
      select k.id, k.application_id, k.user_id, k.is_active, k.allow_cross_domain, k.cross_domain_list
      from max_kb_application_api_key k
      join max_kb_application a on a.id = k.application_id
      where k.secret_key = ?
        and k.deleted = 0
        and a.deleted = 0
      """;

  private static final String FIND_USER_KEY = """
      select id, user_id, is_active, allow_cross_domain, cross_domain_list
      from max_kb_user_api_key
      where secret_key = ?
        and deleted = 0
      """;

  public static boolean isApiKey(String token) {
    return token != null && (token.startsWith(APPLICATION_PREFIX) || token.startsWith(USER_PREFIX));
  }

  public static ApiKeyPrincipal resolve(String token) {
    if (!isApiKey(token)) {
      return null;
    }
    boolean application = token.startsWith(APPLICATION_PREFIX);
    Row record = Db.findFirst(application ? FIND_APPLICATION_KEY : FIND_USER_KEY, token);
    if (record == null) {
      return null;
    }
    String[] crossDomainList = record.get("cross_domain_list");
    if (crossDomainList == null) {
      crossDomainList = new String[] {};
    }
    return new ApiKeyPrincipal(record.getLong("user_id"), application ? record.getLong("application_id") : null,
        Boolean.TRUE.equals(record.getBoolean("is_active")),
        Boolean.TRUE.equals(record.getBoolean("allow_cross_domain")), crossDomainList);
  }

  /**
   * 密钥主体：userId 是密钥所属账号，applicationId 只有应用密钥才有。
   */
  public record ApiKeyPrincipal(Long userId, Long applicationId, boolean active, boolean allowCrossDomain,
      String[] crossDomainList) {

    public boolean applicationKey() {
      return applicationId != null;
    }
  }
}
```

拦截器在原有的令牌校验之前先分流：命中密钥就走进密钥分支，明文令牌不再参与 JWT 校验。密钥分支做四件事——密钥必须启用、所属账号必须启用且未删除、请求路径必须在密钥范围内、来源必须被允许。下面是拦截器的摘录，登录令牌分支只保留分流点，其余与第 25 章一致：

```java
package nexus.io.maxkb.inteceptor;

import java.util.regex.Matcher;
import java.util.regex.Pattern;

import nexus.io.db.activerecord.Db;
import nexus.io.db.activerecord.Row;
import nexus.io.maxkb.service.ApiKeyAuth;
import nexus.io.tio.boot.http.TioRequestContext;
import nexus.io.tio.http.common.HttpRequest;
import nexus.io.tio.http.common.HttpResponse;
import nexus.io.tio.http.common.HttpResponseStatus;
import nexus.io.tio.http.common.RequestLine;
import nexus.io.tio.http.server.intf.HttpRequestInterceptor;
import nexus.io.tio.utils.hutool.StrUtil;

public class MaxKbAuthInterceptor implements HttpRequestInterceptor {

  /** 带应用 ID 的路径，用于比对密钥的应用范围。 */
  private static final Pattern APPLICATION_PATH = Pattern.compile("^/api/application/(\\d+)(/.*)?$");

  /** 账号状态与令牌版本，登录令牌分支与密钥分支共用。 */
  private static final String ACCOUNT_STATE = """
      select role, is_active, deleted, token_version
      from max_kb_user
      where id = ?
      """;

  @Override
  public HttpResponse doBeforeHandler(HttpRequest request, RequestLine requestLine, HttpResponse responseFromCache) {
    String authorization = request.getHeader("authorization");
    String rawToken = authorization == null ? null : authorization.replaceFirst("(?i)^Bearer\\s+", "");

    // 密钥是不透明字符串，不进下面的 JWT 校验分支
    if (ApiKeyAuth.isApiKey(rawToken)) {
      return doBeforeApiKeyHandler(request, requestLine, rawToken);
    }

    // 登录令牌分支：解析令牌、校验账号状态与令牌版本、按前缀校验管理员权限与资源归属，
    // 通过后 TioRequestContext.setUserId(userId) 并 return null；这里只保留分流点，完整实现见第 25 章。
    return null;
  }

  private HttpResponse doBeforeApiKeyHandler(HttpRequest request, RequestLine requestLine, String rawToken) {
    ApiKeyAuth.ApiKeyPrincipal principal = ApiKeyAuth.resolve(rawToken);
    if (principal == null || !principal.active()) {
      return deny(HttpResponseStatus.C401);
    }
    Row account = Db.findFirst(ACCOUNT_STATE, principal.userId());
    if (account == null || !Boolean.TRUE.equals(account.getBoolean("is_active")) || account.getInt("deleted") != 0) {
      return deny(HttpResponseStatus.C401);
    }
    String path = requestLine.getPath();
    if (!withinKeyScope(principal, path) || !acceptsCaller(principal, request)) {
      return deny(HttpResponseStatus.C403);
    }
    TioRequestContext.setUserId(principal.userId());
    return null;
  }

  /** 应用密钥只能访问所属应用的接口；账号密钥不额外限制路径。 */
  private boolean withinKeyScope(ApiKeyAuth.ApiKeyPrincipal principal, String path) {
    if (!principal.applicationKey()) {
      return true;
    }
    if (!path.startsWith("/api/application/")) {
      return false;
    }
    Matcher application = APPLICATION_PATH.matcher(path);
    return !application.matches() || principal.applicationId().equals(Long.valueOf(application.group(1)));
  }

  private HttpResponse deny(HttpResponseStatus status) {
    HttpResponse denied = TioRequestContext.getResponse();
    denied.setStatus(status);
    return denied;
  }

  // …acceptsCaller 见下文…
}
```

范围判定用路径里的数字应用 ID 比对，所以 `/api/application/{其他应用ID}/api_key` 这类请求会被拦下；`/api/application/chat_message/{会话ID}` 这样的路径本身不带应用 ID，它由业务层的会话归属校验兜底——只有会话的 `client_id` 本人或管理员才能继续提问。

认证通过后，请求上下文里的账号就是密钥所属的账号，后续会话创建、聊天记录归属、知识库检索都按这个账号执行，业务代码不需要知道这次调用用的是密钥还是登录令牌。

跨域设置只作用于密钥调用，同源请求与服务器之间的调用直接放行，因此不会影响界面自身的请求：

```java
  /** 跨域设置只作用于密钥调用：同源请求或未声明来源的调用直接放行。 */
  private boolean acceptsCaller(ApiKeyAuth.ApiKeyPrincipal principal, HttpRequest request) {
    String origin = request.getOrigin();
    if (StrUtil.isBlank(origin)) {
      return true;
    }
    String host = request.getHost();
    if (host != null && origin.contains(host)) {
      return true;
    }
    if (!principal.allowCrossDomain()) {
      return false;
    }
    String[] allowed = principal.crossDomainList();
    if (allowed == null || allowed.length == 0) {
      return true;
    }
    for (String item : allowed) {
      if ("*".equals(item) || origin.equalsIgnoreCase(item)) {
        return true;
      }
    }
    return false;
  }
```

## 七、调用示例

密钥就是 Bearer 令牌。第三方集成时先用应用的 Base URL 与密钥开一个会话，再用会话 ID 提问，问答按 SSE 流式返回：

```bash
# 1. 用密钥开一个会话，返回 chat_id
curl -X GET "http://127.0.0.1:10060/api/application/695640157413023744/chat/open" \
  -H "Authorization: Bearer ${API_KEY}"

# 2. 用同一个密钥提问，SSE 流式返回
curl -N -X POST "http://127.0.0.1:10060/api/application/chat_message/${CHAT_ID}" \
  -H "Authorization: Bearer ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"message": "你好"}'
```

返回的第一段是过程事件，后面是逐段增量内容：

```text
event:agent_status
data:{"phase":"context","message":"正在读取会话上下文"}

event:agent_status
data:{"phase":"retrieving","round":1,"query":"你好"}

data:{"is_end":false,"chat_id":"695949624775057408","content":"您好","node_type":"ai-chat-node"}
data:{"is_end":false,"chat_id":"695949624775057408","content":"。已收到","node_type":"ai-chat-node"}
```

## 九、验收结果

验收在管理员界面与一个临时账号上完成，实际观测到的行为如下。

**创建与落库。** 在界面上点击 **Create** 后列表立即出现新密钥，库中记录为：

```text
secret_key          | application_id     | user_id | is_active | allow_cross_domain | cross_domain_list                           | deleted
application-be8038… | 695640157413023744 | 1       | t         | t                  | {http://127.0.0.1:5678,https://dataease.io} | 0
application-a1ae38… | 695640157413023744 | 1       | t         | f                  | {}                                          | 0
```

密钥形如 `application-` 加 32 位十六进制随机串，`create_time` 由数据库默认值写入，界面上的创建时间与之一致。

**接口与界面互认。** 界面上新建的密钥可以直接用于接口调用；反过来用接口创建的密钥也会立刻出现在界面列表里，两级密钥的列表接口都返回数组。

**路由定位准确。** 应用密钥接口与应用分页接口共用前缀，同一个地址稳定返回密钥数组，不会命中应用分页接口。

**密钥调用问答。** 用界面创建的密钥开会话并提问，会话创建返回 200 与 `chat_id`，问答接口按 SSE 流式返回内容，事件序列正常：

```text
GET  /api/application/{应用ID}/chat/open      → 200 {"code":200,"data":"695949624775057408"}
POST /api/application/chat_message/{会话ID}   → event:agent_status … data:{"content":"您好"} …
```

**停用与删除立即失效。** 停用密钥后，同一个密钥再次调用返回 401；删除后同样返回 401，且列表中不再出现该密钥。

**访问范围。** 应用 A 的密钥访问应用 B 的密钥列表返回 403，访问知识库接口也返回 403：

```text
GET /api/application/{应用B}/api_key  → 403
GET /api/dataset/1/20                 → 403
```

**跨域按配置放行。** 同一个密钥（来源列表为 `http://127.0.0.1:5678` 与 `https://dataease.io`）在不同来源下的结果：

```text
不带 Origin                     → 200
Origin: http://127.0.0.1:5678   → 200
Origin: http://evil.example.com → 403
```

**账号隔离。** 临时普通账号访问管理员应用的密钥列表与新增接口返回 403，删除该应用的密钥同样返回 403，这些请求在拦截器按应用归属就被拒绝。用该账号修改或删除管理员的账号密钥（`/api/system/api_key/{管理员密钥ID}`）时，路径不带应用 ID，请求进到服务层后按 `user_id` 过滤查不到记录，返回业务失败码 400 与提示「密钥不存在」。两次尝试之后管理员的密钥状态与内容都没有被改动，两级密钥列表各自只返回自己的密钥。

**账号状态联动。** 停用密钥所属账号后，该账号的密钥调用返回 401；重新启用后恢复 200。

- 初始化脚本已包含密钥表的迁移，可重复执行；`cross_domain_list` 使用 PostgreSQL 原生数组类型，不需要额外扩展。
- 后端构建跳过签名即可，例如 `mvn -DskipTests -Dgpg.skip=true package`；Java 版本为 21，文本块语法可直接使用。
- 前端沿用官方界面，无需额外定制即可对接上述接口；密钥原文只在应用概览的密钥对话框里展示，复制按钮依赖浏览器的剪贴板权限。

## 十一、已知取舍

- 密钥明文展示与复制沿用官方交互，利于第三方对接；如需更严格的管理，可在展示层改为掩码加一次性复制。
- 应用密钥创建后不再变更归属：应用被逻辑删除后，认证时关联不到应用，密钥随之失效，但记录仍留在库里，需要清理时可以按应用 ID 另行删除这些记录。
- 停用与删除都是即时生效的库内状态，不做本地缓存，因此每次调用多一次按键查表；密钥量级很小，代价可以忽略。
- 账号密钥的界面入口按 x-pack 角色显示，当前部署不显示该入口，符合官方前端的角色约定。
